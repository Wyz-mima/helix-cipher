• 未经过第三方审计的部分：自研层（Feistel + Lai-Massey + Sponge）、Helix、 PL 证明层、HX-DYAD 双密钥层与 HX-VEIL 混淆层（v24.1.0 新增，见文末版本说明）、 HX-KDF 自研密钥派生（v24.2.0 新增，取代 PBKDF2；结构类 Argon2 但实例化未经独立审查）、 SM4 / SM3 的自研实现（算法是国密标准，但这份实现无认证）、 以及全部周边逻辑（KDF 参数、链式认证、填充、头部解析）。统计测试合格，但无人做过密码分析。
• 不是认证级 FIPS 140-3 L3：那需要把硬件模块送进 CMVP 实验室测评， 属载体问题，纯软件拿不到。
• 重要数据请优先使用成熟方案（如 VeraCrypt、硬件加密盘、 经认证的密码管理器）。本工具适合作为最极端情况下的额外一层备份，而不是唯一依靠。

加密文件 双密钥模式

离散对数层（DL）基于离散对数困难性，是经典攻击下的额外一族冗余。 但 Shor 算法可在量子计算机上多项式时间求解离散对数，故本层不具备抗量子性。
默认关闭：关闭时为十一层（PL证明层 → 格层(LWE) → LPN层 → 自研层 → 国密 SM4 → ChaCha20 → ZUC(LFSR族) → Helix-CTR → AES-256-GCM → HX-DYAD（自研双密钥，最外层加密层） → HX-VEIL（自研混淆，最最外层））；勾选后为十二层（DL 插在格层与 LPN 层之间）。除 DL 外其余各层均抗量子，格层（LWE）本身即是抗量子的一族。
关于最外两层（HX-DYAD / HX-VEIL）：DYAD 是本轮新增的自研双密钥分组密码（双密钥各最高 512 位，海绵结构，安全界 2320），VEIL 是自研混淆层（严格可逆、长度保持，不是加密、不提供机密性，作用是对付「密文统计特征与自动化剥离」）。两者都是强制层（无开关），位于 AES-256-GCM 之外 —— 越靠外越先被碰到，攻破最外层不等于碰到内层任何一层。 仅在你需要最大经典冗余时勾选（代价：1MB 多约 30 秒）。
勾选后解密端会自动识别（标志写在文件头），无需手动记忆。
TAS-Q 铠封层：在本工具所有用到哈希的位置（头部 MAC、逐块认证 tag、文件级封印、明文摘要） 并联一道零哈希、零非对称原语的封印 —— 原哈希一个不动。
原语为 AES-256-CMAC + 双 AES-256 级联，四层结构（标签层／承诺层／陷门层／8192 轮硬化链）， K1..K4 由 mac 密钥经 SHA-2 ⊕ Keccak 双族派生（输出空间联合 1024 位，但强度上限于 mac 密钥熵 —— 口令模式下即两条口令的组合熵，输出空间大 ≠ 熵大）；Shor 无攻击目标（无非对称原语）。
★ v24.2.1 订正（合并 v24.0.3 审计 W3）：此前此处写的是「密钥域联合 1024 位，Grover 折半后仍余 256 位」—— 失实：K1..K4 的种子源是 mac 密钥（32 字节），1024 位是输出空间而非熵，真实强度上限是 mac 密钥熵。另需注意：TAS-Q 密钥派生自 mac 密钥，与哈希体系同源 —— 「两条结构无关的防线」仅在原语与构造层面成立，不覆盖「mac 密钥泄露」场景（该场景下哈希防线本就已失守）。
为什么是并联而不是替换：哈希一旦被攻破，由本层独立承担防篡改；反之亦然。 攻击者须同时攻破两条结构无关的防线。
代价：单次封印约 0.35 秒，逐块 + 文件级共（块数 + 2）次 —— 1 MiB（17 段）约 6 秒额外开销，文件体积增加约 261 × (块数 + 2) 字节。
勾选后解密端会自动识别（标志写在文件头第 6 位），无需手动记忆。 关闭时字节流与 v23.5.3 完全一致，已加密文件不受影响。
密码本模式：在全部十一层之内、紧贴明文处再加一层传统密码本替换。加密后会额外生成一个 .hlcb 密码本文件（约 16 KB，明文可读、不加密），必须离网分离保管。
· 它解决的不是数学问题，而是密钥分离：即使口令泄露、操作系统被攻破、外层十一层全被剥开，只要攻击者手上没有这本密码本，他拿到的仍是被密码本替换过的中间态，而非明文。
· ★ 必须如实说明的强度边界：密码本在数学上是多表替换，不是信息论安全、也远弱于外层任何一层；它提供的是密钥分离与巨大的密钥空间（(256!)64 ≈ 2107000，暴力不可行），其强度完全依赖「密码本不在攻击者手里」这一前提。与密文存放在同一台已被攻破的机器上 = 没有这一层。
· 解密时不提供密码本：可只解外层十一层，输出仍是密码本态的版本，由你对照密码本手工还原（文件名会加 .密码本态.bin 后缀以防误认）。
· 密码本不参与密钥派生：主密钥与口令体系完全不受它影响，丢失密码本不影响外层十一层的正常解密。

  ⑤ 如实边界（关于"串行计算深度"的主张，勿夸大）：按 pc 档实测分解，内存填充 + 2 趟搅拌 ≈ 38.7s（94.6%），60 万步串行链 ≈ 2.2s（5.4%）。串行深度是真实的，但只占 5.4%，92% 以上仍是内存带宽型成本（与 Argon2 同类型）。绝对不可压缩时间 2.2s/次猜测，对比被它取代的 PBKDF2-210k（约 0.7s）强约 3 倍，不是数量级。HX-KDF 的价值定位是"与 Argon2id 串联的第二条独立攻击曲线"，不是"比 Argon2 更强"——若它被攻破，系统回落到"双 Argon2id"水平（下限未降）。

  ① 为什么去掉 PBKDF2：它的 210k 次 HMAC-SHA512 迭代是纯串行计算，困难性类型单一（只能靠"每次迭代都真的算"拖时间），强度远低于本方案要求的量级；且它与串行链类构造功能重叠 —— 保留它只会拉长耗时、不增加独立的攻击维度。
  ② HX-KDF 构造（五阶段，纯自研）：播种（duplex 吸收 ikm+盐+ctx+参数+outLen，挤出 160 字节种子）→ 内存填充（N 个 160 字节块，块地址由前一块内容导出，数据依赖寻址，抗并行）→ 多趟搅拌（伪随机序 + 内容依赖双引用，类 Argon2 的 pass）→ 长串行收敛链（chain 次严格串行置换迭代，无法并行、无法用内存换时间；每 4096 步混入一个内容依赖内存块，"只推终态不存内存"的攻击在此失效）→ 输出（全轮 squeeze）。双主力论证：Argon2id 的硬化来自内存填充 + 数据依赖寻址（抗 GPU/ASIC 并行），HX-KDF 的硬化来自大内存填充 + 多趟搅拌 + 长串行链（串行计算深度），两者困难性类型不同 —— 攻击者必须同时付出内存带宽成本与串行计算深度成本，缺一条即拿不到 ikmKey，进而 13 个层密钥全部失效。
  ③ 档位（界面可选，与 Argon2 档位并联）：PC 档 = 256 MiB 内存 / 3 趟搅拌 / 60 万步串行链（Node x86 实测 22.1s）；移动档 = 64 MiB / 2 趟 / 6 万步（实测 3.5s，独立进程 RSS 增量 66.7 MiB）。所选档位的四个参数（mKiB / passes / chain / rounds）编码为 16 字节写进文件头（OFF_HXK），解密端读头照用。
  ④ 为什么参数必须进文件头：四个参数全部参与播种（吸收进 seedBuf）—— 解密端若用错参数，得到的不是"降级输出"而是完全不同的 ikmKey，文件直接解不开。故与 Argon2 的 m/t/p 同理念：文件自描述所用成本参数。解密端按当前档位做内存预算校验（与 Argon2 同款），防伪造头部迫使手机付出 256MiB 级计算。
  ⑤ 浏览器主线程友好：HX-KDF 以生成器实现，异步驱动每 65536 步让出一次（setTimeout），22s 的计算不冻结页面；异步驱动与同步驱动输出逐字节一致，由启动自检（KAT 第 22 项）现场锁定。
  ⑥ 格式升级 0xC3 → 0xC4：ikmKey 与全部 13 个层密钥的派生路径改变，密文字节与 MAC 覆盖范围（头部 fixed 区新增 16 字节）均已改变。v24.1.0（0xC3）的 .hlx 本版解不开（已登记为 LEGACY_VER16，会给出明确提示），需用 v24.1.0 解密后重新加密。
  ⑦ 范围声明（只改该改的）：密钥文件（.hlk）的保护路径未动 —— 它仍走「单次 Argon2id + PBKDF2-SHA512(210k) + HKDF」，保护的是信封而非数据本体，且改动它会作废全部存量 .hlk；本轮按「只改后两层（dyad/veil 所在的派生链）」的口径执行。HX-DYAD / HX-VEIL 两层本身零改动（算法、KAT 向量、字节流均不变）。
  ⑧ 如实边界：HX-KDF 是自研算法、无第三方审计，其内存填充/搅拌在结构上类 Argon2（被广泛审计的设计模式），但本实例化未经独立审查；它的价值定位是与 Argon2id 串联的第二条独立攻击曲线（串行计算深度），不是"比 Argon2 更强"。若它被攻破，系统强度回落到"双 Argon2id"水平；若 Argon2id 被攻破（含侧信道/实现缺陷），HX-KDF 仍构成独立障碍。v24.1.0 及更早的 .hlx 需先用对应旧版解密后用本版重新加密。

  ① HX-DYAD 构造：海绵／duplex 结构，置换宽度 1280 位（40 × 32 位字），速率 640 位（80 字节）／容量 640 位 → 海绵安全界 2^320（高于 AES-256 的 2^256）。非线性层为素数域乘法：q = 2^32−5（最大的 32 位素数），y = (mulmodQ(x, c) + a) mod 2^32 —— 非线性与差分抗性来自 mod-Q 与 mod-2^32 两种群的进位混合，不是查表 S 盒。双股编织：偶数位字由 K_A 驱动、奇数位字由 K_B 驱动，两套密钥展开互相独立 —— 改 K_B 对 K_A 的材料零影响（隔离性由 KAT 21 项实测验证）。扩散层 4 趟 x[i] ^= rotl(x[j], rr)，每条变换逐条对合可逆（逆 = 反序重放）。模式为自研 HX-DYAD-SST（自同步 duplex，吸收的是密文而非明文），长度保持、逐块推进。
  ② 双密钥：K_A / K_B 各最高 512 位（合计 1024 位），由 L4 密钥根 dyad 派生 128 字节后对半切开。密钥展开全自研（全宽迭代、状态即密钥、公开常量 SCHED_MUL / SCHED_ADD / SCHED_SEED），不用 HKDF／SHA。
  ③ HX-VEIL 构造：四道严格可逆变换（P1 字节双射 + 位置扰动、P2 正向扩散链、P3 逆向扩散链、P4 分块位置置换），长度保持、逐字节可逆；每块盐 veilSalt 把 ivVeil 搅成 (iv1′, iv2′, tweakShift) 三量，同一密钥在不同块／不同文件输出互不相同。如实边界：VEIL 不是加密、不提供机密性 —— 它是对付「密文统计特征与自动化剥离」的混淆层，抗剥离价值与密码本同类。
  ④ 格式升级 0xC2 → 0xC3：新增两层的密钥流必然改变密文字节，故必须升格式。头部第 7 位 FLAG_DYAD 记录两层状态，0xC3 下恒置 1（两层为强制层；保留该位是为将来若放开可选层时向后兼容），解密端对 (flags & FLAG_DYAD) === 0 做 fail-closed 校验。v24.0.2 及更早的 .hlx 本版解不开（0xC2 已登记为 LEGACY_VER15，会给出明确提示），需用旧版解密后重新加密。

  ② .hlk 内层密钥流跨文件重复（中危）：chunkIV 派生未纳入每文件随机的 kfIv，同保护口令的多个 .hlk 五层流完全相同；破外层 GCM 后两文件 inner 直接 XOR 即得两把主密钥的 XOR。已改为 salt 用 kfIv。
  ③ 启动自检从未被调用：上一版新增的 selfCheckCrypto 只有定义、零调用点 ——「装了锁没接门」。已接入 runKAT() 同一失败通道，并补 σ 差分回归锁（往返测试发现不了 σ 被删除，该锁可以；已用变异体反向验证生效）。
  ④ 格层样本阈值订正：约 97 块（3104 字节已知明文）才达到信息论门槛。此前写的 85 块是把无噪线性代数的 m>n 判据误套到带噪 LWE 上 —— 每样本只泄露 log₂q − H(e) ≈ 13.97 bit（不是 16 bit），故需 21504 / 13.97 ≈ 1539 个样本而非 1344 个。强度声明统一取最小值 经典 ≥2^270 / 量子 ≥2^226（273.9 是 usvp 攻击面，非声明值）。
  ⑤ LPN 层样本阈值同款订正：约 21 块（678 字节），而非「4 块」—— 每样本泄露 1−H(0.25) = 0.1887 bit，需 1024/0.1887 ≈ 5426 个样本。且 LPN 不提供量子侧 128 bit 声明（外推仅 ≈2^110）。
  ⑥ 新增「调用点」自检（第三方审查发现的盲区）：若某次改动让 encryptBlock 把 chunkIndex 钉死为常量且两端同错，则往返测试、KAT 16.5/16.8 全部通过 —— 它们直接调层函数并传入不同 index，绕过了调用点，而后果是全文件所有 chunk 复用同一 s / 掩码序列（v18.1 格层事故同款模式）。新增 katChunkBinding()：插桩记录层函数实收的 chunkIndex，真实走一次 encryptBlock，断言序列为 0,1,2。已用变异体验证生效。
  ⑦ 域分离常量统一登记：双 MAC / LPN / LWE / 层 IV / 自研层子密钥全部靠字符串域分离，新增层时若笔误撞域会静默同源、往返全过。已在启动自检中登记全部 18 个 label/magic 并断言互异，且用生产函数本身取值比较（不是拿字面量再调一次，那样两边同步出错仍不同）。
复审同时推翻了我自己提的一个要求：我曾要求「把 headerMAC 验证前置到版本检查之前」，复审证明那是净损失 —— MAC 需要 macKey、而 macKey 来自 KDF、KDF 输入读自未认证头部，等于把满血 Argon2id(1GiB) 暴露给任意伪造头部（DoS 放大）。当前次序正确，已把规则写进注释防止未来回归。

实测结论（务必先看）：小波域并非更安全。57 张真实照片的卡方值对分析显示，嵌入率 ≤0.25 bpp 时两者几乎持平（未检出率 96.5% vs 94.7%）；但 0.50 bpp 时小波域为 0/57，反而远差于空域的 87.7%。两者本质都是 LSB 替换，都会把自己那个域的直方图值对推平，区别只在暴露在哪个域。决定能否被检出的是嵌入率，不是变换域。

· v19.1 修复：可否认模式 × 硬件密钥 / 额外口令 的冲突：此前外层（诱饵）也被绑上硬件因子与额外口令，导致光有诱饵密码根本打不开外层——因为还需要那把实体钥匙，而 PRF 输出烧录在芯片里无法导出、无法转交，你交不出诱饵层，可否认性反而失效。现改为：硬件 / 额外口令只作用于隐藏层，外层永远只用诱饵密码 A+B 即可打开。解密端改为读取每层自己的 flags 字节（偏移 6）自动匹配因子，新旧格式均兼容。
· v19.1 新增：可否认模式（可选，不影响普通 .hlx）： 勾选后生成 .hlxd 双密码容器 —— 同一文件里放两份数据，外层用诱饵密码、 隐藏层用主密码，各自独立加密（独立盐 / IV）。无痕设计：开头是普通 .hlx 魔数、无容器标识；长度与偏移经 AES-GCM 加密（密钥由密码 HKDF 派生）， 不给密码定位不到隐藏层；填充与密文统计上不可区分。 不勾选时与 v18.8 完全一致，旧文件不受影响。
· v18.8 严重修复（格式兼容）：修复「加密/解密期间 切后台导致文件静默作废」。原先页面切到后台 60 秒会无条件清零密钥库， 但一次加密往往要跑好几分钟，切后台是常态 —— 密钥被销毁后 joinSecret 静默返回全零继续跑完，用全零密钥加密， 界面照样提示「加密成功」，产出的是永久无法恢复的废文件。 修复两处：① 操作进行中推迟清零，结束后再决定； ② joinSecret 还原出全零即抛错（32 字节随机密钥恰为全零的概率约 2^-256）， 把这类静默损坏变成明确报错。
· v18.6 严重修复（格式兼容）：密钥文件（.hlk）读写两侧 ctx 不一致， 导致 KF_VER=0x07 的密钥文件一个都读不出来。写侧用 HelixKeyFile-v18.0、 读侧用 HelixKeyFile-v17.0；ctx 会进入 HKDF 的 info，于是派生出的密钥不同， AES-GCM 认证必然失败并误报「保护口令错误或密钥文件已损坏」。 即：v18.0~v18.5 生成的 .hlk 从诞生起就无法被读回， 若主密钥只存在密钥文件里则等于永久丢失。 修复：提取 KF_CTX 单一常量供两侧共用，从结构上杜绝再次错位。 此前生成的 .hlk 用本版即可正常读取（文件格式未变，只是读侧算错了）。
· v18.5 运行时防护修复（格式兼容）：口令明文字节的清理 此前只在成功分支执行。加密/解密失败时（口令错、文件损坏、读盘失败）， keyA / keyB 的明文字节仍留在内存，口令输入框也没清空 —— 配合失败计数惩罚（连续失败要等更久），等于在内存里累积多次尝试的口令， 堆快照或内存换页到磁盘即可捞到，且失败次数越多残留越多。 修复：清理移入 finally，无论成功、失败还是中途抛异常一律清零， 并补上异常路径的 KeyVault.zeroizeAll()（派生的密钥分片此前也不回收）。
· v18.4 安全修复（0xB9，格式变更）：修复内层静默损坏。 此前的认证只覆盖密文：块 tag 对密文做 HMAC，文件封印只含明文长度； 而六个内层（格 / DL / 自研 / Helix / ChaCha / SM4）全都只做变换、不做认证。 实测后果：DL 层开关与加密时不一致时，解密照样"成功"， 返回 80/80 字节全错的乱码，文件封印也照样通过（因为长度没变）—— 用户拿到坏文件却毫不知情。此缺陷由 DL 层触发，但同样影响其余五个内层。 修复：把每一块【明文】滚动进一个 SM3 摘要，纳入文件封印（流式、内存 O(1)、文件仍为 64 字节封印）。 格式变更：v18.2/v18.3 的密文与本版不兼容，需先解密出原文件再重新加密。
· v18.3 加固（格式兼容）：SM4 层 S 盒加入抗缓存时序处理。 SM4 每分组 32 轮 × 4 次查表 = 128 次 S 盒访问，比 Helix 层更密集， 原本全程共用同一张表，可被 Prime+Probe 一类缓存侧信道利用。现改为准备 16 份副本、 每份置于随机大池的随机偏移处，每 8 个分组换一份。 只改变表的内存位置，不改变查表数值 —— SM4 官方向量与文件格式均不变， v18.2 加密的文件可直接解密。已验证：换槽 100 次后官方向量仍成立、跨版本输出逐字节一致。 性能代价约 +60%（1 MiB SM4-CTR 由 70ms 增至 112ms）。 须说明：这不是常数时间实现，JS 引擎有 JIT、预取与硬件预取器， 无法给出常数时间保证；此举提高攻击成本，不消除攻击面。
· v18.2 安全修复（0xB8，格式变更）：格层（LWE）两处缺陷，均经统计验证—— ① 跨 chunk 密钥流复用：掩码原先只由「密钥 + 块索引」决定，而块索引在每个 chunk 内都从 0 重新开始，导致每 64 KiB 掩码完整重复一次。外层任一族若被攻破， 攻击者拿到一个已知明文块即可解开其余所有 chunk 的对应块。已改为把 chunk 索引 一并纳入 LWE 公开矩阵 A 的 nonce（只能用公开的 chunk 索引，不能用 chunkIV——后者由主密钥派生， 混入会让 A 变成密钥相关，退回 v17.0 之前那个已修复的构造性缺陷）。 ② 掩码退化：q = 65537 时 b 的两个取值（0 与 65536）都会让低 16 位为零， 使该样本的两个明文字节原样穿出格层。实测 320000 个样本中修复前出现 10 次（理论 9.8 次），修复后为 0。 v18.0/v18.1 加密的文件与本版不兼容，需解密后重新加密。
· v18.0 格式变更（0xB7）：新增国密层 —— SM4-CTR（GB/T 32907-2016， 128 位分组 / 128 位密钥，32 轮 Feistel 结构），位于自研层之外、ChaCha20 之内。 它与 AES(SPN)、ChaCha20(ARX)、Helix(SPN 变体)、格层(LWE) 的困难性假设均不相同， 构成独立的一族。同时新增 SM3（GB/T 32905-2012）供完整性用途。 注意：使用国密算法不等于通过商用密码认证 —— 本工具未经任何认证， 此处仅作为标准算法的一层。SM3 / SM4 均以国家标准附录的官方测试向量校验， 见「自检」。旧版 .hlx / .hlk 需先用旧版解密后重新加密。
· v17.0 格式变更（0xB6）：新增第七族 —— 格层（LWE）：b = <a,s> + e mod q，基于格上的容错学习问题。LWE 抗量子（量子下无已知多项式算法，NIST 后量子标准 MLWE 即基于此族），也是与前六族都不同的困难性假设。同时离散对数层改为可选（默认关闭）—— 因 Shor 算法可解离散对数，关闭时全部层级均抗量子。关闭时为五层：格层 → 自研层 → ChaCha20 → Helix → AES-GCM；勾选 DL 后为六层。（注：此处原文曾误写为「Helix → ChaCha20」，与 v13.0 说明及代码实际次序相反，已订正。）
· v16.0 格式变更（0xB5）：新增第六族 —— 离散对数层（DL）：mask = 低32字节(gk mod p)，p 为 RFC 3526 2048 位安全素数。它的困难性假设（离散对数）与前五族（SPN / ARX / Feistel / Lai-Massey / Sponge）完全不同，已知明文攻击者要跨块预测 mask 必须解离散对数。注：本层不具备抗量子性（Shor 可解离散对数），真正兜底抗量子的仍是 AES-256-GCM。
· v15.0 格式变更（0xB4）：修复自研层架构弱点——v14 三层共用同一轮函数（SHA-512⊕Keccak），两哈希同时被破则三层一起塌。本版改为三种不同构造：Feistel 用并联双哈希、Lai-Massey 用 Davies-Meyer 构造、Sponge 直接用 Keccak-f[1600] 原生置换（不经哈希）。另加层间白化破坏层间代数关系，轮数 12→20。旧版 .hlx / .hlk 需先用旧版解密后重新加密。
· v14.0 格式变更（0xB3）：新增自研层（最内层）—— Feistel + Lai-Massey + Sponge 三层复合，轮函数 = SHA-512 ⊕ Keccak-256（两个不同族哈希）。四种结构（SPN / ARX / Feistel / Lai-Massey / Sponge）互不相同的数学基础，即使 AES-256-GCM 与 ChaCha20 同时被攻破，自研层仍保护数据。代价：吞吐约 20 KB/s，1MB 文件约需 1-2 分钟，请耐心等待且不要关闭页面。（此为 v14.0「五层」时的实测值，已不适用于当前版本：v23.3 为八层／九层，实测纯数据吞吐约 6.1 KiB/s，1MB 约需 3 分钟；手机再加上 Argon2id 桌面档的固定开销，小文件也可能要两分钟。详见文末审计附录「性能实测」一节。）旧版 .hlx / .hlk 需先用旧版解密后用本版重新加密。

· 密钥分片驻留：master 与 mac 密钥在内存中以 3 片 XOR 分片保存，仅在单次块运算内临时重组，用完立即 wipe，缩小完整密钥暴露窗口。
· 全文件链式认证：每块 tag 绑定上一块 tag，文件尾追加独立封印 MAC，任何重排 / 截断 / 替换 / 回滚都会被链式校验拒绝。
· headerMAC 覆盖全部头部字段，解密时先验后解，防止 KDF 参数被篡改后触发无意义解密。
· 每块 AAD 绑定 magic / version / kdfId / kdfParams / salt / baseIV / fileId / 时间戳 / 总块数 / 块大小 / 块索引 / 是否末块 / 密文长度，外层 AES-GCM 再绑一次 chunkIV。
· 明文在加密前填充至 1MiB 整数倍，隐藏真实文件长度。
· 密钥文件使用 AES-256-GCM + 独立 Argon2id（256MiB, t=10, p=1）保护，文件内不含明文密钥，A/B 通过 pairId 配对。
· 文件名解密后做消毒，防止路径遍历。单文件硬上限 256MiB。
· 纯 JS 无法保证恒定时间，也无法防御浏览器 0day、扩展、供应链、内存转储、键盘记录；JS 字符串不可变，密码无法真零化。高价值场景请配合 TEE / HSM / 硬件密钥。

→ 单调关系是「σ 越小越弱」（目标向量 = 误差向量，范数 ≈ σ√n，越短越易区分）。本层比 Frodo1344 弱约 17.6 bit。旧注释「强度不低于 Frodo1344」把推理写反了，已删除。
m 敏感性：m=16 ／ 512 不可行（样本不足）；m=2n=2688 → 273.9；m=∞ → 273.9 → 越过 2n 阈值后收敛，前提成立。
限定：2^273.9 是 MATZOV 经典模型下的值；换 core-SVP 等保守模型会低数十 bit（例：Kyber512，MATZOV 143.8 vs core-SVP ≈118）。

三、PL 层高级分析（原判「做不了」，后改为可计算形式完成）
对象：12 轮无白化 Feistel，半块 128 bit，F = KMAC256(rks[r], ·, "Helix-PL-f") 截断至 128 bit。

· 线性：不枚举 LAT（规模 2^128 × 2^128 = 2^256，物理不可枚举），改为推导掩码一致性约束后穷举活跃模式。
  约束：a_(j−1) = b_j，u_j = b_(j−1) ⊕ a_j，a_j = b_(j+1)；F 活跃 ⟺ b_j ≠ 0；零轮间距 ≥ 3
  并查集精确求解：可行模式 129 种，最少活跃 8 轮（最优模式 110110110110；活跃轮数分布 {8:15, 9:56, 10:45, 11:12, 12:1}）
  随机 F 的 LAT 最大相关度：std = 2^-64，2^256 项中最大值 ≈ 2^-59.76；8 轮累积 → 2^-478.1
  所需已知明文块 N = 1/ε² = 2^956 ≫ 全码本 2^256 → 即使拿到全部可能明文也不成立

· Gröbner ／ 代数：判据为「d 阶导数非零 ⟺ 代数次数 ≥ d」。实测 provF 的 1~16 阶导数全部非零 → 次数 ≥ 16。
  Keccak 轮数对照（验证增长律）：R=1→1，R=2→2，R=3→4，R=4→8，R=5→≥17 → 指数增长，饱和于 128（理论最大值）
  单项式数（C(128,k) 累积）：deg 2 → 2^20；deg 4 → 2^61.7；deg 8 → 2^198.9；deg 16 → 2^644；deg 128 → 2^11382
  → 仅「写下方程组」就需 2^198 个单项式，攻击不可行

· 不可能差分：Markov 精确计算（逐轮使用独立 F，与真实 12 个轮密钥一致；半块 5 bit，状态空间 1024），r=10 仍有约 6.4×10^5 条。
  成因：DDT 存在结构性零项（约 37%），该性质对 m=5 与 m=128 同样成立 → 属无白化 Feistel 的固有性质，非本实现缺陷
  但要找出一条需先算出 128 位 F 的完整 DDT，代价 2^256 → 存在但不可发现，登记为残余风险

· Luby-Rackoff 可证明下界：半块 n=128，12 轮 ⊇ 4 轮，取 4 轮界作下界；优势达 1 需 q = 2^64 个明文块 = 2^69 字节 = 512 EB → 不可行

· 缩尺实证（先证明方法本身有效，再谈结果）：阳性对照 —— 1 轮置换的弱 F 得 z=+218.8、带线性结构的 F 得 z=+49.9，均被强检出；
  再测真实 F：DDT 非零率 0.3943 vs 随机基线 0.3931；12 轮差分／线性差值 ≈ 0.00 ／ +0.07 bit；Feistel 输出 2 轮内代数饱和（15/16）
  → 「未发现缺陷」是在方法已被验证有效的前提下得出的，不是方法失灵

七、密钥文件（.hlk）的加密方式
· 主密钥来源：crypto.getRandomValues 生成两个 256 位真随机数（7865 行），不经口令派生，暴力搜主密钥为 2^512。
· 但必须分两种威胁模型（v23.3 订正：此前「不受口令熵限制」的表述片面）：① 仅密文泄露 —— .hlk 未落入攻击者手中，攻击面就是 2^256 真随机主密钥，确与口令无关。② 密文与 .hlk 同时泄露 —— .hlk 是包裹主密钥的数字信封，其 KEK 由保护口令经 Argon2id（256MiB）派生；攻击者无需去解 2^256 的数学难题，只需离线爆破该保护口令即可剥开信封取得真随机主密钥，整体强度坍塌至保护口令熵，与手动密码模式无区别。故该说法仅在情形①成立；.hlk 必须与密文分开保管，保护口令不可弱。
· .hlk 内部七层（v23.3 起，内→外）：PL证明层 → 格层(LWE) → LPN层 → 自研层 → 国密 SM4 → ChaCha20 → AES-256-GCM。未含 Helix 与 DL —— 前者为自研、无第三方审计，后者不抗量子，二者不增加实际安全性。（v23.4.1 措辞订正：此处原写「与 AES 同族」，推理不成立 —— SM4 同为 SPN 却在 .hlk 内；诚实的区分是「标准算法 vs 自研」）。
· v23.4 明确决定、v23.4.1 维持：.hlk 不同步新增 ZUC，维持七层（已知差异，非遗漏）。故主文件九层、.hlk 七层是有意的设计差异。理由：① .hlk 的现实威胁是离线爆破保护口令（GLM 第 2 轮判定），加层不改变该下界；② 同步需升 KF_VER 至 0x0A 并保留旧读路径，改动面大而收益低。故主文件十层、.hlk 七层是有意的设计差异，已在本文显式声明 —— 若将来有人认为这是遗漏而"顺手补齐"，请先重读本条。
· v23.3 修复：PL / LPN 此前未同步进 .hlk：这两层是 v23.x 加入主文件的，当时只改主文件、漏了 .hlk（又一次「改了 A 忘了 B」）。旧 .hlk（KF_VER=0x08，五层）仍可读、不作废；新生成的为 0x09（七层）。新旧两侧用 KF_CTX / KF_CTX_V2 分开派生层密钥，绝不混用。主密钥不变，已加密的文件无需重加密。

九、Gemini 第三方审查（第 1／2 批源码）
送审范围：deriveKeys（L4 分层密钥派生）、deriveLayerIV、provPRK／provExpand／provF／lrEnc32／lrDec32／provMask／provProcess（PL 证明层）。三条结论逐一处置如下。

· ① L4 两级派生（10 个独立根）—— 确认有效，无需改动
审查意见：第一级由 ikmKey 派生 10 个 root_i 并立即导入为 extractable:false 的原生 CryptoKey，密钥材料移出 JS 可读堆；第二级用各自独立的 layerSalt_i 派生工作密钥。任一层泄露受 HKDF 抗原像性与不可提取属性限制，既无法上溯 ikm，也无法横向推导他层。

· ② deriveLayerIV 拼接歧义 —— 判定为误报，但隐患真实，已永久封死
审查意见：'Helix-L4|iv|' + label || baseIV || index 中可变长的 label 与 baseIV 之间无定界符，存在滑动边界碰撞，举例 label='pro' + baseIV 首字节 0x76 ≡ label='prov' + baseIV 首字节被截去。
核算结果：该示例不成立。两条消息的实际长度分别为 51 与 52 字节（12 + len(label) + 32 + 4），长度不等 ⟹ HMAC 输入不同 ⟹ 不可能碰撞。另对全部层标签（helix／dl／cust／sm4／chacha／prov／gcm）× 随机 baseIV × 索引穷举 28.8 万组，碰撞 0；且标签集合中不存在任何前缀关系。
单射性证明：变长段位于最前，其后两段定长（32 + 4）。两消息相等 ⟹ 总长相等 ⟹ len(label) 相等 ⟹ 标签字节相同 ⟹ baseIV 相同 ⟹ index 相同。
但该证明的唯一前提是「baseIV 恒为 32 字节」——此项此前未被强制。若将来某调用点传入其它长度，长度论证失效，前缀关系即退化为真碰撞。故已做三处加固（字节不变，格式仍 0xC1，无需重加密）：
  (1) 抽出 layerIvMsg(label, baseIV, index)，deriveLayerIV 与自检共用同一份构造，杜绝两处失同步；
  (2) 函数内 assertLen('layerIvMsg','baseIV',baseIV,IV_LEN)，把前提变成硬约束；
  (3) 自检新增 A0c：标签前缀关系检查 + 单射性实测 + 「断言必须存在」检查。
变异体反证：删掉 assertLen 那一行后重跑自检 → 立即 FAIL：layerIvMsg 未强制 baseIV 长度（滑动边界防护被移除）；恢复后 PASS。

· ③ PL 证明层双坝 —— 确认有效，无需改动
审查意见：prk（HMAC-SHA512，Merkle-Damgård 族，前缀 0x04 / 域串 Helix-PL|prk）与 prk2（KMAC256，海绵族，域串 Helix-PL-rk2）不经同一哈希体系，所依赖的数学假设正交；域分离标签完全错开。if (prk2 === prk) 的别名陷阱防御被评价为「极具防备心的工程实践」。

· 本次审查的方法学记录：第三方在②上给了错误结论（示例长度算错），但其结构性质疑方向是对的 —— 一个依赖「调用方永远传 32 字节」的隐含前提，本就该显式强制。本项目反复出现的失效模式正是「未被强制的前提被后来的改动打破」，故即便结论为误报，防御仍然加上。

审查意见：当 b 命中 0 或 65536（概率约 2/65537）时改用均匀字节流拼接的 16 位整数，使剩余 65535 个非零状态的微观权重极微弱增加。但 LWE 困难度建立在含 CBD(η=2) 噪声的 ⟨a,s⟩+e 上，这种发生在密文格式化末端的 O(2-16) 偏差不足以被任何已知格还原算法（BKZ 等）利用。

· ③ lweSecret 尾部零填充碰撞 —— 成立，已修复
审查意见：bindBytes 长度可变（12~32）置于 blk 末尾且无定界符，尾部靠初始零补齐；bindBytes = B12 与 bindBytes = B12 || 020 产生完全相同的 72 字节消息 → 秘密向量 s 100% 碰撞。
复核结果：成立。（与第 1／2 批的 deriveLayerIV 不同 —— 那次变长段在最前、后随两段定长，长度论证使其不可能碰撞；本次变长段在末尾，长度论证失效，碰撞真实存在。）实测两组输入构造出的 blk 逐字节相同。
实际可利用性：为零 —— 全部调用点恒传 32 字节 baseIV，不存在短输入路径。但该前提从未被强制，且 lweErrorStream 早已断言 32 字节、lweSecret 却容差 12~32，属内部口径不一致，正是本项目反复出现的失效模式。
修复：lweSecret 改为 assertLen(bindBytes, 32)，与 lweErrorStream 完全同口径。实测：32 字节输入下派生字节流逐字节不变，格式仍 0xC1，无需重加密。自检新增 A0d：短 bindBytes 必须被拒 + s 对 chunkIndex 敏感。

· ④ LPN 内积 AND-奇偶 + τ 判决 —— 确认正确，无需改动
审查意见：lpnInner 的 (aw & s32[w]) 正确对应 GF(2) 按位乘法（v23.0 曾误写 XOR，会使实例退化为 1 维），配合 0x6996（4-bit 奇偶真值表）完成常量时间 popcount parity，无侧信道。eMat[i] < LPN_TAU_NUM 中 LPN_TAU_NUM = 64（已核对源码第 6671 行），SM3 流字节 0~255 均匀分布，严格小于判决给出精确 τ = 64/256 = 0.25，无取模偏置。

· ⑤ aNonce 不含块索引 —— 确认安全，无需改动
审查意见：块索引未丢失，而是作为 ChaCha20 内部计数器平移量 blockIndex * LPN_CC_PER_BLK（lpnAMaterial 内含越界检查），各块独占互不重叠的 PRF 输出区间，密码学上等价于每块独立 Nonce，同时避免频繁重置流状态。

· 方法学补记：第 1／2 批中第三方结论为误报（长度算错），本次为真缺陷。两次的共同点是——问题都出在「调用方永远传 32 字节」这类未被强制的隐含前提上。本项目 12 次事故中绝大多数属此型，故无论结论是否为误报，一律补上硬断言 + 自检锁。

十一、Gemini 第三方审查（第 4 批源码：秘密分片 · KeyVault · .hlk 密钥文件）
送审范围：splitSecret／joinSecret／wipeShares／KeyVault、kfDeriveKeys、readKeyFile（含 0x08／0x09 双路径）。三条结论逐一处置如下。

· ① XOR 分片与 (n,n) 门限 —— 确认有效，无需改动
审查意见：前 n−1 个分片由 randomBytes（CSPRNG）生成，末片为 XOR 校验和，构成标准布尔秘密共享；少于 n 个分片时联合分布与随机噪声不可区分，完美保密、0 bit 优势。joinSecret 就地 XOR 不产生中间副本被评价为「优秀的内存安全实践」；全零拦截（识别后台清零导致的全零密钥）被评价为「极为敏锐」。
必须同时声明的可用性代价（GLM 第2轮补充）：(n,n) 门限意味着零冗余 —— 任一片丢失、损坏或版本不匹配 = 该文件永久不可恢复，无兜底、无恢复途径。这是为了实现完美保密而做的刻意取舍（fail-closed），不是缺陷，但用户在决定是否使用分片前必须知道。

· ② KeyVault 大池与生命周期 —— 确认有效，风险已由既有锁覆盖
审查意见：离散化大池破坏密钥的内存连续性，显著提升内存扫描工程门槛；但 store 持强引用，若 release 因异常或疏漏未执行则分片驻留。核查结果：该风险已在 v23.2 被锁住 —— 自检统计加／解密两侧 release 次数，必须相等且 ≥ 9，删一行即报「加密侧 9 vs 解密侧 8」。另有 zeroizeAll() 兜底（页面切后台 60 秒触发）。无需新增改动。

· ③ plIvBits 盐值不一致 —— 不成立缺陷，但结构异常，已统一
审查意见：0x09 中除 plIvBits 用公开的 kfIv 作 HKDF salt 外，其余所有层密钥均用内部派生子盐 sub.hkdf，派生树不封闭，建议统一。
核查结果：安全性上不成立缺陷 —— ① kfIv 已被外层 AES-GCM 的 additionalData: head 认证，篡改即解密失败；② RFC 5869 明确允许 HKDF salt 公开；③ ikmKey 极高熵，公开 salt 无法逆推。但该项结构异常真实存在：kfIv 同时又是外层 GCM 的 nonce，一个值兼任两个角色，与同源隔离原则不符。
已修复：plIvBits 的 salt 改为 sub.hkdf。唯一性不受影响 —— 此结论有前提（GLM 第2轮点名，勿写成无条件）：sub.hkdf 由 kfSalt 经 deriveSubSalts 派生，其每文件唯一性完全依赖 kfSalt 每文件随机。已目验确认：makeKeyFile 中 kfSalt = randomBytes(KF_SALT_LEN)，每次调用取新值。若将来有人改掉这行（例如改为固定盐或复用），本条结论立即失效，v21.2 的跨文件密钥复用事故会以更重形态复活（这次是密钥本身跨文件相同）。该前提已登记进「不可弱化前提」清单。实测七层往返 14/14 PASS，格式仍 0xC1，主文件无需重加密。
注意：0x09 是本版才引入的新格式，若此前已生成过 0x09 的 .hlk，需重新生成一次（0x08 旧文件不受影响，仍可读）。

十二、Gemini 第三方审查（第 5 批源码：自研层 · SM4-CTR · 主管线编排）
送审范围：custEncrypt／custDecrypt、sm4Ctr／deriveSm4Nonce、encryptBlock（含层序与 wipe 时序）。三条结论逐一处置如下。

· ① 自研层级联构造与 Sponge 域分离 —— 确认有效，无需改动
审查意见：Feistel + Lai-Massey 串接后 XOR 一层独立密钥（rk3）驱动的海绵流，属「防线堆叠」；即便前两层自研轮函数存在高概率差分特征或线性逼近，末尾的流仍起 OTP 式掩蔽，密文底线安全性不低于 Sponge 流本身。spongeKeystream(seed, rk3, chunkIV, i) 中 chunkIV 为定长 32 字节，天然充当定界符，不存在滑动边界歧义。

· ② SM4-CTR Nonce 隔离 —— 确认正确，无需改动
审查意见：deriveSm4Nonce = chunkIV.slice(16, 32) 占 [16,31]；ChaCha20 用 chunkIV[0..11] 占 [0,11]；两者之间还有 4 字节（12~15）隔离带，物理上完全不重叠。

· ③ 条件式擦除的「指针别名」陷阱 —— 成立，已修复（本轮唯一真缺陷）
审查意见：if (本层key && 上层key) wipe(上一缓冲) 在任一层被跳过时彻底失效 —— 被跳过的层让本层输出退化成指向上一缓冲的别名，两个条件同时为假 ⇒ 上一缓冲永不擦除，滞留 JS 堆等待 GC。
复核结果：成立且可达。第三方举例「关闭自研层」在生产路径上不可达，但 DL 层是界面复选框、默认关闭（useDL = !!(dlEl && dlEl.checked) ⇒ dlShares=null ⇒ dlKey=null），走的是同一条缺陷路径。实测（原样加载真源码、插桩记录各层输出缓冲、以默认配置调用 encryptBlock）：
  修复前 → lat: 共 1 个输出缓冲，未清零(泄漏) 1 个（格层 64 字节中间态零擦除）；lpn / cust 因下一层有密钥而侥幸被擦。
  修复后 → 三者均为 0 个泄漏，且入参明文 raw 未被误擦。
为什么不能简单降级为 if (本层key)：内层全被跳过时 cur 仍是调用方入参 raw，会被误擦、破坏调用方数据。故改为 owned 标记跟踪 + step(next, produced)：只有本层真正产出新缓冲时才擦除上一缓冲。
解密侧无需改动：decryptBlock 用的正是正确写法 if (本层key) wipe(上一缓冲)（其入参恒为 GCM 解出的新缓冲，不存在误擦风险）。加密侧是唯一的错处。
自检新增锁：源码文本中若出现 if (A && B) wipe( 即判 FAIL，并要求 owned / step( 两标记存在。变异体反证：改动前副本 → FAIL: 条件式擦除 6 处；修复后 → PASS。

十四、Gemini 第三方审查（续轮：威胁模型视差的另外两处）
第三方在确认前三项（串联成本锚定主密钥熵、格层参数映射、.hlk 数字信封）之后，主动指出本系统还存在两处隐含假设坍塌，均已采纳并写入免责声明。

· ① 「离线 + 源码未篡改 = 安全」—— 不成立
审查意见：文档中隐式假设只要 HTML 源码未被篡改且离线运行，数据即安全。但持有 <all_urls> 权限的第三方扩展（语法检查、网页翻译、密码管理器等）其 Content Script 运行在比网页更底层的特权级别，可在 Helix 的 JS 触发加密之前直接读取 DOM 中输入框的明文，或 Hook 底层 API 截获刚输入的保护口令。本地离线并不能防御浏览器进程内的恶意扩展。
处置：已写入免责声明第七节，并明确要求处理高敏数据前在干净浏览器环境（无扩展 / 隐私窗口 / 专用设备）中运行。

· ② 内存清零对「进程冻结与快照提取」无效
审查意见：TamperGuard 与 zeroizeAll() 的成立前提是 JS 事件循环仍在正常运行、有时间执行清零。若威胁上升到操作系统级 —— 恶意软件直接 Dump 浏览器进程内存、系统休眠产生 hiberfil.sys、冷启动攻击 —— 浏览器运行状态被瞬间冻结，探针根本没有机会被触发，KeyVault 大池中的分片将以当时离散状态直接暴露。
处置：已写入免责声明第七、八节。结论是：基于内存清零的防御只对「运行时逻辑异常」有效，对「进程冻结与快照提取」无效；离散化能抬高内存扫描门槛，但抬不高到可对抗物理快照。
